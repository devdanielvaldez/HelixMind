# AgentMesh integration

Recurring PubMed discovery is available through `medai_literature_watch_register`, `medai_literature_watch_claim_due`, and `medai_literature_watch_refresh`; schedules are session scoped, use a daily minimum interval and overlapping PubMed entry-date windows, and consume the session research budget. The AgentMesh `work --watch` worker claims due schedules, retains bounded PMID snapshots and hash-backed discovery events, reports when PubMed's total exceeds the 200-ID retrieval cap, and retries transient errors. It fetches title, publication date, journal, DOI, and PMCID for at most 20 newly discovered PMIDs per refresh; `medai_literature_watch_papers` exposes this compact bibliographic metadata. Abstracts are not retained, and new PMIDs remain discovery leads: the watch does not validate claims or create evidence automatically. List, disable, and event-history tools are also available.

The gateway also exposes budgeted gene and protein annotation searches, UniProtKB full-entry/domain/PDB cross-reference lookup, residue-level PDBe SIFTS mapping, IntAct/PSICQUIC interaction evidence with deterministic pair reconciliation, AlphaFold DB predicted structure lookup, ClinicalTrials.gov record lookup, and Reactome pathway analysis. UniProtKB entries, SIFTS mappings, IntAct MITAB evidence/reconciliation, AlphaFold DB models, ClinicalTrials.gov snapshots, and Reactome results retain provider identifiers/input hashes as task-attributed artifacts.

Run medai-science execute <session-id> as a worker client and configure MEDAI_AGENTMESH_URL to this gateway. The worker does not call scientific source APIs directly: it claims and completes jobs, and invokes PubMed/ClinicalTrials.gov MCP tools through AgentMesh. Artifact reads use database cursor pages with a total byte/item/page ceiling; if a complete artifact set exceeds that bound, the task is moved to needs_review instead of analyzing a partial set. Handlers that have not passed scientific validation stay in needs_review.

The MCP tools include atomic task claiming, lease renewal, recovery of expired work, worker-bound checkpoints and completion updates, and cooperative research cancellation in addition to source and evidence operations. Expired leases are retried with durable exponential availability delays (5 seconds initially, capped at 300 seconds) within the five-attempt ceiling; the workspace shows attempt count and scheduled retry time. Long-running workers renew leases and resume from the most recent durable checkpoint; cancellation skips queued work and lets the active bounded source operation return before marking its task skipped.

Request cancellation with `medai cancel <session-id>` or the AgentMesh capability `biomedical.research-session-cancel`. The MCP handlers poll the durable session flag during provider/model requests and cancel the active HTTP coroutine; the worker then finalizes the task as skipped. Expired active leases are recovered as skipped instead of being retried. Worker progress checkpoints are lease-owner-bound and are exposed under `biomedical.research-task-checkpoint`.

AgentMesh is the governed capability and MCP execution plane; MedAI owns biomedical research state and scientific semantics. This integration uses the public AgentMesh contracts instead of copying its implementation into this repository.

AMCP contracts in capabilities/ cover research-session creation and model-assisted objective query planning, disabled Python/R capability source drafting and sandbox validation, same-language paired benchmarking, PubMed retrieval and optional title-only reranking, loopback-only PMC result annotation and claim-pair semantic screening, graph snapshots, protein structure and residue mapping, interaction lookup, protein annotation records, ClinicalTrials.gov record lookup, Reactome pathway analysis, hypothesis workflows, and the leased task lifecycle: claiming, renewal, recovery, and completion. The research worker now routes evidence inventories, bounded cross-paper claim screening, contradiction-search candidate retrieval, graph snapshots, hypothesis proposal/criticism, and reproducibility report generation through the governed MCP gateway. Claim-pair screening refreshes and verifies each PMC source and candidate hash, requires both exact source licenses in the operator allowlist, uses only loopback inference, persists categorical outputs and provenance without sentence text, and always requires human review. Screening receipts bind the model-visible title, abstract, and methods context with canonical metadata hashes and bounded character lengths. The registration script validates and installs every package in that directory.

Completed research sessions also produce a deterministic, versioned MedAI research-DAG topology proposal. The proposal validates dependencies, records only hashes of source-run task outputs, and remains disabled pending authenticated review. It is stored with the reproducibility artifacts. This domain proposal is not AgentMesh Teach Workflow IR and is not executable by AgentMesh runtimes.

## Contracts

- Learned operational procedures are AgentMesh Workflow IR `1.0` YAML.
- Outcome-oriented capabilities use AMCP `0.1` packages with explicit authority, effects, recovery, provenance, and implementation bindings.
- MCP services exposed to researchers are registered/routed through AgentMesh. MedAI does not bypass AgentMesh policy to invoke those tools.
- Generated scientific source code is stored and evaluated by MedAI's isolated runner. It is never loaded into the AgentMesh gateway process.

The MedAI scientific package exposes a Streamable HTTP MCP server (`medai-mcp`) with tools for session creation/listing, reading and updating dependency-aware research tasks, applying a hash-verified objective task scope, checking/charging execution credits, PubMed, ClinicalTrials.gov search and NCT snapshot lookup, MyGene.info, ClinVar variant-record search, UniProtKB, IntAct/PSICQUIC, AlphaFold DB predicted structure lookup, and Reactome analysis, recording evidence, storing task-attributed content-hashed artifacts, and evidence-linked graph updates. The Research Director applies the validated task scope before specialist claims; excluded DAG stages receive audited `skipped` status without task-start charges. Executed task starts and bounded source queries are charged against session credits and retained as audit events. Start the API, then the MCP service. Configure `MEDAI_API_BEARER_TOKEN` identically for API and MCP when the API is bound outside loopback; MCP sends it on every internal API request. Specialist workers instead send their scoped `MEDAI_SPECIALIST_API_TOKEN` in the MCP request `_meta` field. The server validates that token at `/v1/auth/whoami` and uses it for the whole request through a context-local header scope; AgentMesh preserves the MCP JSON-RPC body while filtering caller HTTP Authorization headers. Configure matching `MEDAI_API_TOKENS` entries with `role: service` and `scientific_agent_id`, and do not pass the general service bearer into specialist worker containers. Their task claims, transitions, leases, checkpoints, credit charges, evidence, artifacts, and graph writes are checked against the credential's assigned DAG role. `config/agentmesh-medai.yaml` points AgentMesh's static upstream at that server; run AgentMesh with that file to govern client traffic through its gateway. In Compose, only loopback ports are published.

Set `MEDAI_AGENTMESH_CATALOG` to the AgentMesh capability catalog directory before registering the AMCP package. The registration script validates and installs through AgentMesh's own CLI. Registration does not provision source credentials, authenticate the MCP server, or grant caller permissions; configure those controls before exposing the endpoint beyond a trusted local network.

For administrative control-plane access, configure `AGENTMESH_CONTROL_URL`, `AGENTMESH_ADMIN_TOKEN`, and optionally `AGENTMESH_TENANT` / `AGENTMESH_NAMESPACE`. Use `medai-science agentmesh status` and `snapshot` for authenticated runtime discovery; the control API exposes active snapshot resources, not a desired-resource listing endpoint. Snapshot reads are bounded and their SHA-256 digest is recomputed over the revision and canonical resource list before they are returned. `apply <resource.json> --expected-revision N` applies one explicit `kind`/`name`/`state`/`spec` resource with optimistic concurrency, while `reconcile` asks AgentMesh to publish desired state to the active gateway. The client rejects remote cleartext HTTP, follows no redirects with the bearer credential, and bounds JSON responses. MedAI's capability-route synchronizer supports reviewed-plan rollout, signed journaling, snapshot verification, and rollback of confirmed writes; uncertain outcomes enter explicit operator recovery instead of automatic retries.

Generate a local desired-route plan with `medai-science agentmesh plan-capabilities --service medai-mcp`. It reads the AMCP catalog and gateway configuration, writes a deterministic SHA-256 plan, and marks only `verified`, `production`, and `production_certified` capabilities active; all other lifecycle states are disabled. Catalog defaults are experimental, so a reviewed JSON map keyed by `capability-id@version` can be supplied with `--status-overrides-json`; its bytes are included by hash in the plan. Pass `--output route-plan.json` to retain the review artifact. Planning is read-only: it does not apply resources or reconcile a live gateway. Lifecycle status is administrative metadata and does not establish scientific validity.

Inspect synchronized routes with `medai-science agentmesh sync-status --state-file .medai/agentmesh/sync-state.json`. It verifies the private signed journal and compares its active MedAI routes with the authenticated live snapshot, reporting missing, changed, and untracked routes. It never mutates AgentMesh, creates a signing key, or clears `recovery_required`; an operator must resolve that state before another route write.

Inspect a previously synchronized route set with `medai-science agentmesh sync-status --state-file .medai/agentmesh/sync-state.json`. The command verifies the private signed journal and compares its active MedAI routes with the authenticated live snapshot, reporting missing, changed, and untracked routes. It is read-only: a `recovery_required` result remains blocked for route writes until an operator resolves the control-plane state and reviews the journal.

Semantic capability search only recommends reuse when an authenticated AgentMesh control-plane v1 snapshot in the configured tenant/namespace contains the exact active route for `MEDAI_AGENTMESH_SERVICE`. Set `AGENTMESH_CONTROL_URL`, `AGENTMESH_ADMIN_TOKEN`, `AGENTMESH_TENANT`, `AGENTMESH_NAMESPACE`, and `MEDAI_AGENTMESH_SERVICE` on the MedAI MCP service (or local CLI environment). The control client validates the snapshot digest and does not follow redirects; remote administrative URLs require HTTPS. An absent, draining, wrong-service, or unreachable route cannot authorize reuse. The result records the snapshot revision and digest. Route activity confirms runtime routing state, not scientific validation or reviewer identity.

Reactome gene-list pathway analysis is exposed as `medai_pathways_analyze_reactome` and registered through `biomedical.pathway-analysis`. The official [Reactome Analysis Service](https://reactome.org/AnalysisService/) performs the over-representation calculation; the [Reactome Content Service](https://reactome.org/dev/content-service) exposes curated pathway records. Candidate generation and criticism are exposed through `medai_hypotheses_propose` and `medai_hypotheses_criticize`, with separate AMCP contracts. After generating graph-path candidates, the hypothesis specialist searches PubMed for up to three candidate paths within the remaining-credit budget and retains exact query hashes, coverage receipts, and PMID metadata without abstracts. Researchers can record authenticated relevance and study-context annotations bound to each exact query and paper artifact at `POST /v1/research/{session_id}/hypothesis-literature-reviews`; the review records design, population/model, methods, findings, and limitations without scoring novelty. These searches are discovery leads only; relevance, contradiction, completeness, and novelty require human review, and novelty remains unscored. Criticism outputs are leads for a scientist, not an automated verdict.

Gene–disease evidence is available through `medai_gene_disease_evidence` and `biomedical.gene-disease-evidence`. For EFO IDs it queries [Open Targets GraphQL](https://platform-docs.opentargets.org/data-access/graphql-api), the directly mapped [NHGRI-EBI GWAS Catalog API](https://www.ebi.ac.uk/gwas/rest/api/v2/docs), and the [Monarch Initiative v3 association API](https://api.monarchinitiative.org/openapi.json); for other supported ontology IDs it queries Monarch. Exact stable gene identifiers are joined while native source scores, study links, association categories, evidence meanings, and Monarch primary/aggregator provenance remain separate. GWAS mapped genes can be positional; integrated association scores are not probabilities. Monarch is an aggregated knowledge graph, so provider counts do not represent independent studies. Source/API failures are surfaced per source and do not silently erase successful source records.

Submission-level gene–disease assertions are also available through `medai_gene_disease_gencc_gene` / `biomedical.gene-disease-gencc-gene` (exact HGNC ID or symbol) and `medai_gene_disease_gencc_disease` / `biomedical.gene-disease-gencc-mondo` (exact MONDO ID). They use GenCC's new-format CC0 export, cached with conditional ETag/Last-Modified requests and a 24-hour refresh floor. Each submitter's classification remains a separate assertion with its own record hash and source provenance; the tool does not synthesize a consensus or merge GenCC classifications with PanelApp/Open Targets scores. Restricted OMIM data is absent from the export. See GenCC's [download and programmatic access terms](https://thegencc.org/download).

ClinGen Gene-Disease Validity curations are available through `medai_gene_disease_clingen_gene` / `biomedical.gene-disease-clingen-gene` and `medai_gene_disease_clingen_disease` / `biomedical.gene-disease-clingen-mondo`. Exact HGNC or MONDO queries return separately sourced classifications with inheritance code, SOP, expert panel, classification date, official report URL, and dataset/record hashes. ClinGen's own SOP describes its curation as a time-specific expert appraisal, not a systematic review of all literature; MedAI therefore retains it independently from GenCC assertions, PanelApp scores, and Open Targets associations. The CSV and API entry points are listed in the official [ClinGen downloads page](https://search.clinicalgenome.org/kb/downloads).

The leased worker's `genes.curate` DAG step follows exact human gene resolutions and calls both ClinGen and GenCC through the AgentMesh gateway. If the objective contains exactly one explicit EFO identifier, it also calls `medai_gene_disease_evidence` to retrieve Open Targets, directly mapped GWAS Catalog, and Monarch records. If it contains exactly one explicit MONDO CURIE, it calls the native ClinGen and GenCC disease lookup tools plus Monarch. It never derives disease identity from free text or assumes MONDO/EFO equivalence. Checkpoints are keyed per resolved Entrez gene and source and by the exact disease ID; individual source artifacts, classifications, and assertion counts remain separate. These records do not establish that every returned disease matches the research objective or that an association is causal.

Cross-paper PMC result comparisons use a loopback model only as a categorical screening step. Researchers can record a separate authenticated adjudication at `POST /v1/research/{session_id}/claim-alignment-reviews`; the API rechecks the retained annotation artifact, document hash, candidate hash, and exact two-candidate link before recording the reviewer, relation, population/method comparability, and rationale. Sentence text is not copied into the review, and an `opposing` adjudication does not automatically establish a scientific contradiction.

The final `skills.learn` task calls `medai_skills_learn_research_sequence`. It evaluates disjoint batches of three completed, hash-verified reproducibility bundles and may create an installation-signed, versioned `SKILL.md` candidate when the shared core task sequence succeeded in every source session. Packages are stored under `MEDAI_SKILLS_DIR` and retained as session artifacts. They remain `pending_review` with execution and network access disabled; there is no automatic execution or AgentMesh MCP registration.

Compound chemical identity is available with `medai_compounds_lookup_pubchem` and `biomedical.compound-identity-pubchem`. The adapter resolves a PubChem CID or bounded name query, returns all matches up to a fixed limit, and flags ambiguity instead of selecting a CID silently. Stereochemistry-bearing SMILES/InChI identifiers are retained with PubChem record hashes. When the local `chemistry` extra is installed, RDKit-derived descriptors include the installed RDKit version and their input structure hash. These chemical descriptors do not establish biological targets, activity, efficacy, safety, or clinical relevance. See the official [PubChem PUG REST specification](https://pubchem.ncbi.nlm.nih.gov/docs/pug-rest) for its property and identifier API.

Pharmacology records are available through `medai_drug_profile_chembl` and `biomedical.drug-profile-chembl`. The worker invokes it only for an unambiguous PubChem result with a standard InChIKey; the adapter verifies the exact key against ChEMBL molecule records and queries parent molecule records for provider-reported mechanisms, indications, and warnings. Every returned source row has a content hash and retrieval time. Empty results mean that this bounded provider lookup returned no row, not that no pharmacology or risk exists. ChEMBL warns that these endpoints aggregate parent-drug records; the report remains research-only and is not a clinical recommendation. See the [ChEMBL Data Web Services documentation](https://chembl.gitbook.io/chembl-interface-documentation/web-services/chembl-data-web-services).

Candidate shared target IDs can be screened with `medai_drug_shared_targets_chembl` under `biomedical.drug-shared-target-screen-chembl`. Both compounds must resolve through exact standard InChIKeys; the result intersects ChEMBL mechanism target IDs and retains the hashed provider rows for each side. A shared target is only a candidate pharmacology link and does not establish a drug-drug interaction, potency, clinical exposure, or interaction direction. Separate curated interaction evidence is required before describing an interaction.

Trial snapshot refresh is available through `medai_trials_refresh_and_compare` and `biomedical.trial-refresh-compare`. Recurring monitoring uses `medai_trials_watch_register`, `medai_trials_watch_claim_due`, and `medai_trials_watch_refresh`; the session can list/disable watches and read event diffs or its latest full observation. When `medai-science work --watch` runs, the worker claims due watches with durable leases, charges the session budget, retains record hashes and source-field diffs, retries transient failures, and pauses watches on exhausted budgets. The comparison history begins with MedAI's first session capture; it does not claim historical versions that the current-record API did not return. The [ClinicalTrials.gov API](https://clinicaltrials.gov/data-api/about-api/study-data-structure) describes the current study record shape.

For local CLI research, `medai-science drug aspirin` performs the PubChem resolution followed by the same exact-key ChEMBL lookup; ambiguous compound names stop before joining pharmacology.

Pairwise label screening is available through `medai_drug_interaction_labels_openfda` and `biomedical.drug-interaction-label-screen-openfda`, or locally with `medai-science drug-interactions aspirin warfarin`. RxNorm exact-or-normalized name resolution must yield exactly one ingredient concept; approximate matches and ambiguous combinations stop before label retrieval. Labels are queried by the matched UNII, or ingredient RxCUI when no UNII is available, and returned identifiers are checked before retention. At most five labels per ingredient are retained with set ID, version, effective time, identifiers, interaction-section text, and hashes. The exact-name mention screen reports reciprocal, asymmetric, or no matched label mentions. These are retrieval/review leads only: asymmetry is not a contradiction, missing mentions are not negative evidence, and the tool does not diagnose a drug interaction. openFDA documents its label endpoint and the `drug_interactions` field in the [label API guide](https://open.fda.gov/apis/drug/label/how-to-use-the-endpoint/) and [searchable fields](https://open.fda.gov/apis/drug/label/searchable-fields/). RxNorm search precision is documented in the NLM [findRxcuiByString API](https://lhncbc.nlm.nih.gov/RxNav/APIs/api-RxNorm.findRxcuiByString.html); its API documentation requests this attribution: “This product uses publicly available data from the U.S. National Library of Medicine (NLM), National Institutes of Health, Department of Health and Human Services; NLM is not responsible for the product and does not endorse or recommend this or any other product.”

For source-version review, `medai_drug_interaction_cross_source_review` is registered as `biomedical.drug-interaction-cross-source-review`. It retains up to three current DailyMed SPL records per RxNorm ingredient, retrieves at most two earlier versions per SET ID through the documented v2 history resource and versioned ZIP download, and compares matching SET IDs against openFDA label records. Historical records retain the provider history row digest, archive digest, version/date, and bounded interaction-section text/hash. DailyMed and openFDA may distribute the same FDA-originated SPL content, and earlier versions of one label are not independent clinical evidence; these comparisons expose record changes for review only. History retrieval is bounded and does not claim complete label history. See the official [DailyMed version-history API](https://dailymed.nlm.nih.gov/dailymed/webservices-help/v2/spls_setid_history_api.cfm) and [web-services documentation](https://dailymed.nlm.nih.gov/dailymed/app-support-web-services.cfm).

Crossref DOI resolution and bibliographic search use `medai_papers_resolve_crossref` under `biomedical.paper-crossref-resolve`; set `CROSSREF_MAILTO` to join Crossref's polite pool. The adapter retains DOI-linked bibliographic metadata, dates, deposited license metadata, and bounded publisher/member-deposited references. It does not fetch abstracts, infer claim polarity, or treat citation links as supporting/contradicting evidence. Reference metadata can be incomplete because Crossref records reflect member deposits. See the official [Crossref REST API documentation](https://www.crossref.org/documentation/retrieve-metadata/rest-api/) and [access guidance](https://www.crossref.org/documentation/retrieve-metadata/rest-api/access-and-authentication/).

Exact bioRxiv and medRxiv preprint metadata by DOI is available through `medai_papers_lookup_preprint` / `biomedical.paper-preprint-lookup` and `medai-science preprint`. The adapter retains title, authors, date, version, category, license, published-version metadata, and source hash while omitting the abstract. `medai_papers_search_preprints` / `biomedical.paper-preprint-search` scans at most three pages from a date/category slice of up to 93 inclusive dates, then screens titles and transient abstracts for every lexical query token. Abstracts are not retained; results are bounded and are not semantic or comprehensive search. Neither operation treats a publication link as version identity or establishes peer review. Official [bioRxiv API](https://api.biorxiv.org/) and [medRxiv API](https://api.medrxiv.org/) documentation describes the DOI and paginated date/category endpoints.

`medai_ontology_search` / `biomedical.ontology-ols4` exposes budgeted OLS4 term search and stores a task-linked artifact. `medai_ontology_resolve_identifier` returns only exact matches in OLS identifier fields; it does not infer ontology equivalence or treat provider rank as confidence. See the official [OLS4 API documentation](https://www.ebi.ac.uk/ols4/api-docs).

`medai_ontology_cross_mapping_review` / `biomedical.ontology-cross-mapping-review` retrieves direct (distance 1) EBI OxO disease cross-references and retains the raw response digest and mapping source labels as review candidates. OxO imports mappings from multiple sources and does not validate their evidence; the `genes.curate` worker preserves them as a separate artifact and moves the task to researcher review when candidates are present. It never substitutes an EFO identifier for MONDO or merges their gene-disease records. See the [OxO mapping service](https://www.ebi.ac.uk/spot/oxo/) and its documented [mapping API example](https://faircookbook.elixir-europe.org/content/recipes/interoperability/ontology-alignment-oxo.html).

The drug interaction cross-source review also retrieves at most five PubMed title/abstract candidates after both names resolve to distinct RxNorm ingredient concepts. Its bounded query includes up to six indexed ingredient names per RxNorm concept plus interaction, pharmacokinetic, pharmacodynamic, and selected exposure/outcome terms. PMID records retain publication types, MeSH headings, and selected endpoint-term signals for triage. These are retrieval signals only; they do not establish study independence, actual co-administration, a comparator, exposure, direction, mechanism, clinical relevance, or a drug interaction.

For a candidate carrying a PMCID, `medai_drug_interaction_pmc_fulltext_screen` (`biomedical.drug-interaction-pmc-fulltext-screen`) accepts the same-session literature screen and candidate artifact IDs, fetches the linked BioC document, and returns source-offset/hash leads from methods, results, discussion, and limitations that match resolved ingredient names and pharmacology terms. The persisted receipt omits full-text passages, records the article-specific license, and leaves the interaction verdict null. It does not adjudicate that the pair was actually administered, dose, route, comparator, study design, or label overlap; those require full-text review by a researcher.

An authenticated researcher can record that structured review through `POST /v1/research/{session_id}/drug-interaction-reviews`, binding the note to the screen artifact and candidate location. The API attributes the reviewer from the bearer credential and stores design, pair exposure, comparator, dose, route, endpoints, outcomes, limitations, and label-evidence overlap. The record remains a researcher annotation with `research_only: true`, `clinical_advice: false`, and a null interaction verdict; it is displayed beside the source location in the Literature workspace.

`medai_drug_interaction_review_sources` / `biomedical.drug-interaction-source-review` accepts explicit same-session IDs for one retained openFDA/DailyMed label and either one PubMed candidate or a linked PMC full-text screen. It ranks bounded sentence candidates and sends no more than ten selected pairs to the configured model. PMC screening re-fetches BioC and requires an identical source digest, an exact article-license allowlist entry, and a loopback model provider. Each categorical review lead preserves source artifact hashes, PMID/PMCID or label version, exact field offsets, sentence hashes, and the BioC digest. The result is research-only, requires human review, and sets `interaction_verdict` to null; co-mention and model screening do not establish interaction, contradiction, or clinical relevance.

Crossref reference DOIs are indexed from their retained artifact into a session-scoped `citation_links` relation, readable through `GET /v1/research/{id}/citation-links` and `medai citations <session-id>`. The indexer accepts only same-session `crossref_citation_metadata` artifacts and is idempotent. These DOI edges record deposited citation structure and remain separate from evidence claims and biomedical graph relationships.

`medai_papers_citation_network` returns those captured links plus incoming/outgoing degree and PageRank for each DOI. The calculation uses unique directed DOI pairs and is deterministic over the retained session graph. It is a navigation aid over potentially incomplete Crossref deposits; it does not rank scientific quality, evidence strength, or claim support.

PMC full text can be parsed with `medai_papers_understand_pmc`, backed by the official [PMC BioC API](https://www.ncbi.nlm.nih.gov/research/bionlp/APIs/BioC-PMC/) and `biomedical.paper-fulltext-parse`. It returns section text, annotated normalized entity IDs and unclassified result-sentence candidates to the active caller, while the retained session artifact stores only hashes, section metadata and annotation offsets. Article-specific reuse rights must be checked before further retention or reuse; PMC restricts automated retrieval to its documented APIs and reuse rights vary by article.

Capability search uses `medai_capabilities_search_semantic` and `biomedical.capability-semantic-discovery`. The SQLite index embeds only local AMCP intent/schema text with a materialized model already present on disk. Results retain vector similarity and independent schema/effect/permission checks; lifecycle state comes from the authenticated MedAI capability registry and a local AMCP label cannot promote a capability. The search tool also requires the exact active route in the authenticated AgentMesh runtime snapshot. Reuse remains disabled unless an operator pins a holdout-passing threshold report for that exact embedding-model content hash; the repository has no independent calibration corpus, so it ships no reuse policy. The search tool never executes a result.

Local Rust registry lifecycle commands are available as `medai capabilities propose`, `promote`, `deprecate`, `rollback`, and `history`. They manage the local registry and do not alter the authenticated MedAI API registry. For shared deployments, AMCP imports begin at `pending_review`; lifecycle decisions use the authenticated API and platform-admin review endpoints documented in `docs/OPERATIONS.md`. Route plans consume that API registry snapshot and retain its digest; applying a route plan still requires an explicit reviewed plan digest. Learned Skills can be audited end-to-end with `medai skills agentmesh-status`, which verifies signed local content against the installed AMCP package, its immutable MedAI registration, lifecycle status, and exact AgentMesh route. This synchronization grants access only to the signed review package; Skill execution remains disabled.

Generated Python and R proposal payloads are signed with installation-local HMAC-SHA256 after model usage is attached. The signing key is created with private filesystem permissions at `MEDAI_PROVENANCE_KEY_FILE` (default `.medai/provenance-hmac.key`) or supplied as `MEDAI_PROVENANCE_HMAC_KEY`; Docker Compose stores it on the persistent MedAI data volume. Validation refuses missing, modified, or differently signed proposals before sandbox execution. The signature detects changes relative to this installation's key and does not claim external signer identity or non-repudiation; protect and back up the key as an operational secret.
